# Stacked pull-request validation gap

Observed October 25, 2026: PR46 targets automation-failure-handoff and PR47 targets automation-ci-evidence. The synthetic workflow originally accepted pull requests only into main or mission-scenarios. GitHub therefore emitted no synthetic run for either PR. Its inline source guard independently repeated the same restricted target list. Local suites did not test workflow event delivery, and the workflow inventory checker established byte identity only, not trigger coverage. Passing local tests and absent hosted checks were different states.

The initial bounded repair registered the two existing targets in both places and refreshed the reviewed workflow hash. Hosted runs 40246450012 and 40246459590 passed 234 and 243 tests respectively against their current merge candidates.

The lasting repair removes target-branch filtering from the secret-free synthetic pull_request trigger. New stacked branches receive opened, synchronize, reopened and ready_for_review events without target registration. Push filters are unchanged. This does not broaden manual secret-bearing Notion or Gemini workflows. The source verifier validates the Git ref format, checks the exact checkout, and requires the candidate's two parents to match the independently observed current remote base and event head. It exports that verified base to the subsequent append-only ledger preflight when event metadata is stale.

Six source-verifier regression methods cover a future stacked target, stale event metadata, base movement, wrong head/parent count, malformed remote/ref data, wrong checkout/event/ref and push compatibility. Workflow inventory hashes remain mandatory. Event delivery itself still requires a hosted run; absence of checks must never be reported as passing. Changes to a head or base require fresh merge-candidate evidence. PR review and merge, scheduled maintenance, live log decoding, host-loss recovery and audit gate promotion remain distinct operations.
