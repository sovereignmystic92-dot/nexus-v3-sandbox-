# Durable failure observations

FailureStore in tools/failure_store.py adds local SQLite persistence around the offline collector. ingest(packet) validates normalized evidence and uses BEGIN IMMEDIATE plus synchronous FULL to append unique observations and calculate the active handoff atomically. close() releases the connection. No raw logs, credentials or provider calls are stored or executed.

Run attempts retain their full observation snapshots. Replayed snapshots are ignored. Pending observations can advance; completed metadata/results cannot be rewritten, except enriching an entirely absent case list with matching metadata. Conflicts roll back the batch. The latest attempt for each run controls current findings, successful reruns suppress earlier failures, and stale revisions cannot produce current work. Identical failure signatures across runs share a finding with separate observations. newly_active_findings distinguishes new transitions from repeat delivery; inactive_finding_ids means no longer actionable, not proof of a repair (pending or blocked reruns can also suppress work).

Validation: 243 local tests passed using PYTHONPATH=src python3 -m unittest discover -s tests/unit -q: 234 inherited tests and nine new methods. Tests cover close/reopen, separate Python process, repeated reports, successful reruns, old-attempt replay, cross-run deduplication, pending completion, case enrichment, stale revision, conflicting-batch rollback and injected SQLite insertion failure. This is local synthetic persistence evidence, not host-loss recovery or production durability.

Bounds and limits: the inherited collector caps 100 attempts per run and 100 reports per ingestion; excessive history holds rather than truncates. No compaction or retention policy is installed. The caller must supply a trusted current revision and authenticated normalized evidence. The store does not authenticate database history or detect coherent tampering. Ordinary SQLite locking serializes ingestion; distributed workers, remote fencing and power-loss behavior are untested. No CLI, scheduler, live log decoder, issue creation, patch executor or merge is added. This is state persistence, not a durable work-delivery queue: a future executor needs an outbox/acknowledgment protocol before relying on newly_active_findings across a crash after commit. Consumers can query the current active findings by ingesting an empty reports packet.
